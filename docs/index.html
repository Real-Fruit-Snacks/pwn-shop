pwn-shop

Tool packages for pwn-broker, built from upstream releases

pwn-broker's tool install puts a tool on the machine for one box and takes it off again at finish. This is where those tools come from. Each one is pinned to a version of upstream's own release, so a box I come back to in six months installs the same files, and nothing is installed from a package name that can change under it.

  1. Use itAt the prompt
    tool install certipy

    Nothing to set up. It reads this repository's published index, downloads the zip from its release, checks its size and SHA-256 against the index, and installs it for the box. The first Python tool brings the runtime it runs on.

  2. kerbruteOn PATH
  3. pspyTo upload
  4. certipyWith runtime
  5. playbooksIn the note
  6. FinishAll removed

Box closed out

No network on the Kali machine

Fill a folder while you have one. fetch.sh downloads the index and every zip it names, checks each one, and ends with the line to put in /opt/pwn-broker/config.toml, such as tools_index = "/home/kali/pwn-packages". It is POSIX sh, needs curl and sha256sum and no GitHub account, and changes nothing on the machine but that folder. Run it again after a new build is published; the guide has the rest.

[sh] offline mirror 
git clone https://github.com/Real-Fruit-Snacks/pwn-shop
sh pwn-shop/fetch.sh ~/pwn-packages

What it does

  • Upstream's own filesPinned

    A recipe pins each upstream file by its size and SHA-256, and the build refuses a download where either differs. The files in a package are upstream's own, beside its licence, with two exceptions: Python wheels built from a pinned source archive when upstream publishes none, and Rubeus.exe, which upstream publishes only as source and which is compiled from a pinned commit with a fixed .NET SDK. No tool binary is committed to this repository.

  • For one boxtool install

    Installs the newest build the index lists, for the open box, with no install script. finish removes it again unless another unfinished box still uses it, and the box records which build it had.

  • Four kindskali · upload · both · notes

    Kind kali puts a command on the machine, upload puts files in /opt/pwn-broker/upload to carry to the target, and both does both. A notes package puts nothing on PATH: it holds the playbooks pwn-broker's note window reads with :Pb.

  • Python toolspython-3.13

    A Python tool's dependencies are bundled as wheels pinned by hash, and it runs on the runtime package. A dependency that comes from Git is pinned to a full commit and its archive's SHA-256. The runtime puts nothing on PATH, so Kali's python3 is never used or shadowed, and it comes and goes with the tools that need it.

  • Checked firstCI · Kali offline

    On every change, CI builds each new package, runs build.py check, and installs it with pwn-broker's own code under Python 3.12, 3.13 and 3.14. Then it installs every package again inside the official Kali image with the network off. Only then, on main, does it publish.

  • Never changedkerbrute-v1.0.3-1

    The version is upstream's; the build number is mine, and goes up each time I repackage the same version. A package is named for both, kerbrute-1.0.3-1.zip under the tag kerbrute-v1.0.3-1. A fix is a new build, never an edit to a published one.

  • An index to carryindex.toml

    One file with every build's size and SHA-256. pwn-broker reads the published one by default, or any URL or folder named by tools_index, so a folder filled by fetch.sh works with no network at all.

  • Built anywherebuild.py

    python build.py build <tool> makes a package from its recipe and build.py check tests it. CI has rebuilt kerbrute, ligolo-ng, peass-ng and pspy to their published bytes. The guide has the format, and CONTRIBUTING.md how to add a tool.

A runtime is never installed on its own: it comes and goes with the tools that require it. A notes package needs pwn-broker 0.1.7 or later. Each package carries the licence of the tool in it, and this project is not affiliated with those projects.

Known issues

  • Packages are x86_64 with glibc only. Build 3 of certipy and targetedkerberoast carries wheels for its runtime's Python 3.13 only.
  • The index and the packages are not signed. The SHA-256 values in the index are the only check: they catch a corrupted or swapped zip, not who published the index.
  • kerbrute and pspy publish no checksums upstream. Their pins are the SHA-256 of each file as first downloaded.
  • Kali's own ligolo-ng package also installs a command named ligolo-proxy, and sudo does not use PATH. Use sudo /opt/pwn-broker/bin/ligolo-proxy, the path tool install prints.
  • PEASS-ng's licence has terms beyond the GPL. Read recipes/peass-ng/LICENSE before redistributing the package.
  • The first Python tool on a machine costs the runtime: a 34 MB download and about 100 MB unpacked. Its OpenSSL and other libraries are fixed when a new build of the runtime is published, not when Kali updates.
  • autorecon brings its Python code and dependencies, but its scans call nmap and other Kali system tools, which it does not bring.
  • evil-winrm-py is not a drop-in for Ruby Evil-WinRM: it takes --ssl for -S, has no -s or -e, and its Kerberos extra is not bundled. Kali's Ruby evil-winrm remains separate.
  • penelope 0.21.0 starts a local MCP socket even with --oscp-safe. It is packaged for lab and CTF use, not as an OSCP-safe shell handler; use Kali's nc, ncat or socat for that.
  • PrintSpoofer, SharpEfsPotato, SweetPotato, Hot Potato, SharpGPOAbuse, SeRestoreAbuse, SeManageVolumeExploit and calebstewart's CVE-2021-1675 script have no redistribution licence, and Microsoft's terms forbid republishing AccessChk, so none of them is here. Five other potatoes are.
