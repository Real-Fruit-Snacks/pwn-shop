pwn-shop

Tool packages for pwn-broker, built from upstream releases

pwn-broker's tool install puts a tool on the machine for one box and takes it off again at finish. This is where those tools come from. Each one is pinned to a version of upstream's own release file, so a box I come back to in six months installs the same files, and nothing is installed from a package name that can change under it.

Use it

tool install certipy

At a pwn-broker prompt, with nothing to set up. It reads this repository's published index, downloads the zip from its release, checks its size and SHA-256 against the index, and installs it for the box. The first Python tool brings the runtime it runs on.

No network on the Kali machine: fill a folder while you have one. fetch.sh downloads the index and every zip it names, checks each one, and ends with the line to put in /opt/pwn-broker/config.toml, such as tools_index = "/home/kali/pwn-packages".

git clone https://github.com/Real-Fruit-Snacks/pwn-shop
sh pwn-shop/fetch.sh ~/pwn-packages

It is POSIX sh, needs curl and sha256sum and no GitHub account, and changes nothing on the machine but that folder. Run it again after a new build is published. The guide has the rest.

What it does

Upstream's own files, pinned

A recipe pins each upstream file by its size and SHA-256, and the build refuses a download where either differs. Nothing is compiled or patched: the files in a package are upstream's own, beside its licence. No tool binary is committed to this repository.

Installed for a box, taken off at finish

tool install <name> installs the newest build the index lists, for the open box, with no install script. finish removes it again unless another unfinished box still uses it, and the box records which build it had.

Four kinds of package

Kind kali puts a command on the machine, upload puts files in /opt/pwn-broker/upload to carry to the target, and both does both. A notes package puts nothing on PATH: it holds the playbooks pwn-broker's note window reads with :Pb.

Python tools bring their own Python

A Python tool's dependencies are bundled as wheels pinned by hash, and it runs on the python-3.13 runtime package. The runtime puts nothing on PATH, so Kali's python3 is never used or shadowed, and it comes and goes with the tools that need it.

Checked before it is published

On every change, CI builds each new package, runs build.py check, and installs it with pwn-broker's own code under Python 3.12, 3.13 and 3.14. Then it installs every package again inside the official Kali image with the network off. Only then, on main, does it publish.

Never changed once published

The version is upstream's; the build number is mine, and goes up each time I repackage the same version. A package is named for both, kerbrute-1.0.3-1.zip under the tag kerbrute-v1.0.3-1. A fix is a new build, never an edit to a published one.

An index you can carry

The index is one file, index.toml, with every build's size and SHA-256. pwn-broker reads the published one by default, or any URL or folder named by tools_index, so a folder filled by fetch.sh works with no network at all.

Built the same way anywhere

python build.py build <tool> makes a package from its recipe and build.py check tests it. Builds repeat: CI has rebuilt kerbrute, ligolo-ng, peass-ng and pspy to their published bytes. The guide has the format, and CONTRIBUTING.md how to add a tool.

Tested on

  • Not tested: a full Kali desktop, or a real target. Packages have been installed in the Kali image in CI and by hand under WSL 2.
  • Not tested: the Windows files. No Windows file has been run anywhere, and cdk has not been run in a container. They are upstream's own release files, pinned by hash.
  • The unit suite on Windows 11 under Python 3.13, and on Ubuntu 24.04 in CI under Python 3.11, 3.12, 3.13 and 3.14.
  • Every package in CI, built or downloaded on Ubuntu 24.04, passed build.py check, and installed with pwn-broker's own code under Python 3.12, 3.13 and 3.14, each command started once.
  • Every package in the official Kali image (Kali 2026.3) with the container's network off, before it was published.
  • Builds that repeat: kerbrute, ligolo-ng, peass-ng and pspy rebuilt by CI to their published bytes, and python-3.13 built on Windows and on Ubuntu to the same SHA-256.
  • By hand in Kali 2026.2 under WSL 2: every tool installed by tool install from the published index or a built folder and removed again by finish, as root and as a normal user whose sudo asks for a password; fetch.sh against the real releases, then three tools installed from its folder with the network off.
  • The full record, with counts, runs, commits and dates, is in docs/tested.md.

Known issues

  • Packages are x86_64 with glibc only. Build 3 of certipy and targetedkerberoast carries wheels for its runtime's Python 3.13 only.
  • The index and the packages are not signed. The SHA-256 values in the index are the only check: they catch a corrupted or swapped zip, not who published the index.
  • kerbrute and pspy publish no checksums upstream. Their pins are the SHA-256 of each file as first downloaded.
  • Kali's own ligolo-ng package also installs a command named ligolo-proxy, and sudo does not use PATH. Use sudo /opt/pwn-broker/bin/ligolo-proxy, the path tool install prints.
  • PEASS-ng's licence has terms beyond the GPL. Read recipes/peass-ng/LICENSE before redistributing the package.
  • The first Python tool on a machine costs the runtime: a 34 MB download and about 100 MB unpacked. Its OpenSSL and other libraries are fixed when a new build of the runtime is published, not when Kali updates.
