# Changelog

## Unreleased

- `build.py`: builds a package from a recipe, with a card and a `SHA256SUMS.txt`, and writes the index. Every upstream file is refused unless its size and SHA-256 match the recipe. `check` applies pwn-broker's package rules to the recipes and the zips. `lock` resolves a Python tool's `requirements.in` into a hash-pinned `requirements.lock`. `plan`, `compare` and `notes` are for CI.
- A Python tool's dependencies are bundled as wheels for Python 3.12 and 3.13 on x86_64 Linux. A dependency that publishes no wheel is built from its hash-checked source archive only if the recipe lists it in `build_from_source`; none of the first six does.
- Recipes for `certipy` 5.1.0, `kerbrute` 1.0.3, `ligolo-ng` 0.9.2, `pspy` 1.2.1, `peass-ng` 2026.11.14 and `targetedkerberoast` 2024.12.16.
- `fetch.sh`: downloads the published index and zips into a folder, checks each zip against the index, and prints the `tools_index` line for `config.toml`.
- CI: unit tests, then each package is built or downloaded and installed with pwn-broker's own code under Python 3.12 and 3.13, and every command is started once. On `main` it publishes a release for each new build and replaces the index. A recipe that changes without its `build` going up fails, unless an upstream file can no longer be fetched or matched, which is a warning.
- `record`, `asciinema`, `openvpn`, `ping` and `ip` are now reserved command names, because pwn-broker runs them itself.
- Published: build 1 of each of the six and the index, from the first CI run on 2026-11-15. The repository is private, and the packages and the index are not signed.
- Python 3.14 added: a Python tool's wheels now cover Python 3.12, 3.13 and 3.14, because Kali now ships Python 3.14 and pwn-broker refuses a Python tool on a Python its package does not list. `lock` resolves for every listed Python and, when they differ, names each dependency and what each Python resolved it to.
- Build 2 of `certipy` 5.1.0 and `targetedkerberoast` 2024.12.16, with wheels for Python 3.12, 3.13 and 3.14. `targetedkerberoast` now pins `pycryptodome` 4.5.0 (build 1: 4.4.0), because `requirements.in` leaves it unpinned and the new lock took the newer release; the other dependencies of both are unchanged. Build 1 of each stays published as it is.
- CI: the unit tests also run under Python 3.14, and every package is installed under 3.14 as well as 3.12 and 3.13.
- Runtimes: a package of kind `runtime` carries one Python build from python-build-standalone, byte for byte, and a Python tool names the one it requires with `requires`. A runtime or a tool that requires one is schema 2; every other package stays schema 1, so the published builds of the other tools rebuild byte for byte. Package names may hold a dot. `lock` resolves for the runtime's Python series alone, and the build refuses a wheel that does not fit it, one built from source included. Two tools that require each other are refused with a message rather than a traceback.
- `python-3.13` 3.13.18, build 1: the first runtime, from python-build-standalone release 20261110. Its `LICENSE` holds, each copied byte for byte under its own heading: CPython's licence and pip's licences, from the archive; the licence files the build's `PYTHON.json` names for CPython itself and for the libraries it links, from upstream's full distribution of the same build; and, for what is compiled into the interpreter, CPython's `Doc/license.rst` (mimalloc among it) and the HACL* notice from `Modules/_hacl/Hacl_Hash_SHA2.c`, both at the tag `v3.13.18`. `tools/runtime-licence.py` writes it from those four files. Its manifest's licence reads `PSF-2.0 and others (see LICENSE)`.
- Build 3 of `certipy` 5.1.0 and `targetedkerberoast` 2024.12.16 requires `python-3.13` and carries wheels for Python 3.13 only, so it no longer runs on Kali's own Python. The dependencies are the versions of build 2. Builds 1 and 2 stay published and run on Kali's Python where it is one they list.
- `fetch.sh` accepts a package name with a dot, so it fetches `python-3.13`; before, an index naming it was refused whole.
- CI: the install check installs a tool the way `tool install` does, after its runtime, checks that the tool's environment was made by the runtime's interpreter, and removes both again; a runtime on its own is unpacked and its interpreter must report its version. A new `kali` job installs each recipe's current build inside the Kali image with the container's network switched off, after checking that nothing resolves or answers, and starts each command with `--help` or `-h`. Publishing waits for it. It has run once, on branch `runtimes` at commit a33db87 (GitHub Actions run 43768259174, with pwn-broker at its `runtimes` branch): every job passed, and `publish` was skipped because the run was not on `main`.
